## 1. 동시 방문 신청 시 QR 티켓이 중복 발급됨 (CI 테스트 실패)

**문제 상황**

GitHub Actions에서 `reservation` 모듈의 `VisitApplicationAcceptanceTest.동시_신청_QR_1장만_발급()` 테스트가 실패했다. 동일 고객이 같은 날짜에 방문 신청을 10개 스레드로 동시에 요청했을 때, QR 티켓이 1장만 발급되어야 하는데 `ticketRepository.findAll()`의 결과가 1보다 크게 나왔다.

**원인 분석**

"해당 고객·날짜의 티켓이 이미 있는지 조회 → 없으면 새로 생성"하는 check-then-act 패턴으로 티켓 발급 로직이 짜여 있는데, 이 두 단계 사이에 DB 유니크 제약이나 락이 없다. 여러 스레드가 거의 동시에 "조회" 단계를 통과하면서 전부 "티켓 없음"으로 판단하고 각자 INSERT를 실행해, 동일 조건의 티켓이 중복 생성되는 전형적인 race condition이다.

**해결 방법 (진행 중)**

- 근본 해결책은 (고객, 방문일자) 조합에 DB 유니크 제약을 걸거나, 발급 로직에 비관적 락(`SELECT ... FOR UPDATE`)을 적용해 동시 요청이 순차적으로 처리되도록 하는 것.
- 이번 스프린트에서는 원인만 진단하고 실제 서비스 코드 수정은 다음 스프린트로 넘김.

## 2. Vite 빌드 에러 — `Failed to resolve import '.../BulkConsultPromo'`

**문제 상황**

여러 페이지(참가업체 목록, 차량 상세)에서 공용으로 쓰기 위해 상담 신청 박스를 `BulkConsultPromo` 컴포넌트로 분리했는데, import 하는 코드는 추가됐지만 개발 서버에서 계속 "Failed to resolve import" 에러가 발생했다.

**원인 분석**

컴포넌트를 참조하는 쪽(기존 파일 수정) 작업은 반영됐지만, 정작 새 파일(`BulkConsultPromo.jsx`)을 생성하는 작업 자체가 여러 수정 지시 사이에서 누락되어 파일이 실제로 존재하지 않았다.

**해결 방법**

파일 시스템을 직접 확인해 파일이 없다는 것을 확정한 뒤 누락된 파일을 생성하고, 함께 필요했던 CSS(반응형 처리)도 최신 상태로 동기화했다. 이후 정상 빌드 및 렌더링을 확인했다.

## 3. 화면이 좁아져도 상담 신청 박스가 플로팅 버튼으로 안 바뀜

**문제 상황**

좁은 화면에서 사이드바의 상담 신청 박스가 화면 하단으로 밀려나지 않고, 오른쪽에 작은 플로팅 버튼으로 바뀌도록 구현했는데도 실제로는 기존처럼 하단에 그대로 표시됐다.

**원인 분석**

CSS 파일에 예전 버전에서 쓰던 `@media (max-width: 768px) { .c-bulk-promo { position: static; } }` 규칙이 그대로 남아 있어, 새로 추가한 플로팅 레이아웃 규칙과 충돌하고 있었다.

**해결 방법**

옛 미디어쿼리 블록을 새 플로팅/확장 규칙으로 교체. 이 과정에서 같은 컴포넌트를 쓰는 다른 페이지(차량 상세)도 아직 예전 인라인 구현 방식이었던 것을 발견해 함께 최신 버전으로 맞췄다.

## 4. 머지 충돌 해결 미흡으로 배포 실패 (Vercel 빌드 에러)

**문제 상황**

`dev` 브랜치에 머지한 뒤 Vercel 배포가 실패했다. 에러 로그에 `Identifier 'Link' has already been declared`, `Identifier 'useParams' has already been declared`가 출력됐다.

**원인 분석**

머지 충돌을 해결할 때 `<<<<<<<`, `=======`, `>>>>>>>` 마커만 지우고 두 브랜치의 import 줄을 그대로 둘 다 남겨서, 같은 모듈(`react-router-dom`)에서 `Link`, `useParams`가 중복 선언된 상태로 커밋됐다. 추가로 `useNavigate`를 import는 했지만 실제로 `const navigate = useNavigate();`를 호출하는 줄이 빠져 있어서, 병합만 제대로 해도 또 다른 런타임 에러(`navigate is not defined`)가 날 뻔했다.

**해결 방법**

두 브랜치의 import를 실제로 합쳐 한 줄로 정리하고(`Link`, `useNavigate`, `useParams`를 하나의 import 문으로), 빠졌던 `useNavigate()` 훅 호출을 추가했다. 이후 정상 배포 확인.

## 5. 참가업체 목록에서 부스 묶음이 잘못 합쳐짐/안 나뉨

**문제 상황**

참가업체 목록 페이지에서 같은 업체가 여러 부스를 신청한 경우 "A-101 ~ A-102"처럼 한 카드로 묶여 보여야 하는데, 처음엔 전혀 안 묶이다가, 이를 고친 뒤에는 반대로 같은 회사가 **서로 다른 시점에 별도로 신청한** 부스들(A-101, A-103, A-107, A-109 등)까지 전부 하나의 카드로 합쳐지는 문제가 발생했다.

**원인 분석**

두 문제 모두 "무엇을 기준으로 묶어야 하는가"를 잘못 잡아서 생긴 문제였다.

- 1차 시도: 화면에 표시되는 제목(`title`) 문자열이 정확히 같아야 묶이도록 했는데, 이 `title`은 업체가 부스별로 등록한 "부스 소개 콘텐츠" 제목이 있으면 그걸 우선 쓰는 값이라, 같은 업체라도 부스마다 제목을 다르게 입력했으면 묶이지 않았다.
- 2차 시도: 그래서 회사명(companyName) 기준으로 바꿨더니, 이번엔 진짜 신청 단위(같은 시점에 한 번에 접수한 부스 묶음)와 상관없이 "같은 회사"라는 이유만으로 전부 합쳐져 버렸다. 실제로 묶여야 하는 단위는 회사가 아니라 **하나의 신청(BoothApplicationGroup)** 이었다.

**해결 방법**

백엔드 응답(`CustomerBoothVehiclesResponse`)에 `companyName`(표시용)과 `applicationGroupId`(그룹핑 기준용)를 별도 필드로 추가하고, 프론트엔드의 그룹핑 키를 `applicationGroupId` 기준으로 변경했다. 이렇게 하면 같은 신청으로 한 번에 접수한 부스끼리만 카드로 묶이고, 시점이 다른 별도 신청은 각각 독립된 카드로 표시된다.

**부수적으로 확인한 것**

이 과정에서 "부스 하나가 목록에서 아예 안 보인다"는 현상도 함께 제보됐는데, 이건 그룹핑 버그가 아니라 원래부터 있던 설계(전시 차량이 1대 이상 등록된 부스만 고객 화면에 노출)때문이었다. 버그와 데이터/사용 미비 이슈를 구분해 불필요한 코드 수정을 피할 수 있었다.

## 6. git 저장소에 무관한 파일 수백 개가 "수정됨"으로 표시됨

**문제 상황**

`git status` 실행 시 이번 스프린트에서 건드리지 않은 파일까지 포함해 400개가 넘는 파일이 수정된 것으로 표시되어, 실제 변경 범위를 파악하기 어려웠다. 또한 `.git/index.lock` 파일이 남아 있어 일부 git 명령이 경고를 출력했다.

**원인 분석**

`git diff -w`(공백 무시)로 비교했을 때 대부분의 "변경"이 실제 코드 변경이 아니라 줄바꿈(CRLF/LF) 차이뿐이었다. 이는 실제 작업 내용과 무관한 노이즈였다. `.git/index.lock`은 이전에 비정상 종료된 git 작업의 잔여물로 추정된다.

**해결 방법 / 권고**

커밋 대상을 정할 때 `git status` 대신 `git diff -w --stat`으로 실제 내용이 바뀐 파일만 걸러서 확인하고, 그 파일들만 선택적으로 `git add` 하도록 했다. `.git/index.lock`은 다른 git 프로세스가 실행 중이 아닌 것을 확인한 뒤 삭제가 필요하다.
