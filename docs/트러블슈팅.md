## 부스 참가 승인 후에도 부스가 AVAILABLE로 남아 중복 신청 가능

| 항목 | 기록 |
|---|---|
| 시각, 영향 | 관리자가 부스 참가 신청을 승인해도 Booth 상태가 AVAILABLE로 남아, 결제 완료 전까지 다른 업체가 같은 부스에 계속 신청 접수 가능 |
| 관련 Story | 부스 참가 신청, 승인 기능 (Notion 원본 확인 필요) |
| 관련 계약, Test | `POST /api/admin/booth-applications/{applicationId}/approve` |
| 재현, 증상 | 승인 API 호출로 신청 상태는 SUBMITTED -> PAYMENT_PENDING으로 바뀌지만, `GET /api/exhibitor/expos/{id}/booths` 조회 시 부스 status는 여전히 AVAILABLE. 다른 참가업체가 같은 부스에 재신청하면 201 Created로 정상 접수됨 |
| 확인한 원인 | `approveBoothApplication()`이 신청(BoothApplication) 상태만 바꾸고 Booth 엔티티는 건드리지 않음. 신규 신청 검증(`validateBoothAvailable()`)은 Booth.status만 보는데 이 값을 갱신하는 코드가 없어 검증 기준 자체가 갱신되지 않음 |
| 조치, 담당자 | BoothStatus에 RESERVED(승인 완료, 결제 대기)를 신설해 AVAILABLE -> RESERVED -> ASSIGNED 3단계로 재설계. 승인 시 `booth.reserve()` 호출, 결제 실패, 기한 초과 시 되돌리는 release 내부 API(RESERVED -> AVAILABLE + 신청 REJECTED)를 대칭으로 추가. paymentId 기준 멱등 처리 포함 |
| 정상, 실패 회귀 | curl로 승인 직후 RESERVED 전환, 경쟁 신청 409 차단, release 후 AVAILABLE 복귀와 재신청 가능, 확정, 해제 재요청 시 멱등 no-op까지 수동 검증 완료 |
| Backlog, 설계 조정 | 완전히 동시에 겹치는 승인 요청의 원자성은 아직 미검증. 동시성 테스트(같은 부스 동시 승인 요청 중 하나만 성공하는지)로 재검증 예정 |

## 배포 환경에서만 소셜 로그인 redirect_uri 불일치

| 항목 | 기록 |
|---|---|
| 시각, 영향 | 로컬에서는 구글, 카카오, 네이버 소셜 로그인이 모두 정상 동작했으나 배포 서버에서만 로그인 버튼을 누르면 실패 |
| 관련 Story | 소셜 로그인 (US25) (Notion 원본 확인 필요) |
| 관련 계약, Test | `GET /login/oauth2/code/{registrationId}` (OAuth2 콜백) |
| 재현, 증상 | 카카오: "등록되지 않은 Redirect URI 입니다: http://identity:8081/login/oauth2/code/kakao", 구글: "오류 400: redirect_uri_mismatch". 콘솔에는 로컬, 배포용 콜백 주소가 이미 둘 다 등록되어 있었음에도 발생 |
| 확인한 원인 | redirect_uri는 서버가 매 요청마다 자신이 받은 요청 정보(scheme, host, port)로 조립함. 배포는 nginx(443, TLS 종료) -> gateway(8080) -> identity(8081) 3홉을 거치는데, 각 홉은 자기가 직접 받은 연결 정보만 알아서 identity가 컨테이너 내부 주소 `http://identity:8081`을 기준으로 redirect_uri를 잘못 조립함. 로컬은 프록시 없이 identity에 직접 붙어서 재현되지 않았음 |
| 조치, 담당자 | 1차로 identity에만 `forward-headers-strategy: framework`를 추가했으나 gateway가 nginx의 `X-Forwarded-Proto`를 신뢰하지 않고 내부 값으로 덮어써서 실패. gateway에도 같은 설정을 추가한 뒤 세 제공자 모두 정상 동작 |
| 정상, 실패 회귀 | 배포 환경에서 구글, 카카오, 네이버 로그인 재시도로 정상 콜백 확인 |
| Backlog, 설계 조정 | `NONE`, `NATIVE`, `FRAMEWORK` 옵션 중 `NATIVE`를 직접 비교 테스트하지 않고 `FRAMEWORK`로 확정함. 왜 이 옵션이어야 하는지 비교 검증은 남아있음 |

## 참가업체 차량 조회 API의 N+1 쿼리로 일부 차량이 누락된 것처럼 보임

| 항목 | 기록 |
|---|---|
| 시각, 영향 | 부스를 여러 개 가진 참가업체를 화면에서 하나로 묶는 작업 중, 일부 부스(A-102, A-103)의 차량이 목록에 아예 안 보이는 현상. 원인 추적 중 부스 개수만큼 쿼리를 반복하는 구조를 발견 |
| 관련 Story | 참가업체 차량, 부스 통합 조회 (Notion 원본 확인 필요) |
| 관련 계약, Test | `GET /api/customer/expos/{expoId}/vehicles` (`CustomerVehicleService.getExpoVehicles`) |
| 재현, 증상 | 박람회에 부스가 30개면 이 API 하나가 DB 쿼리 100개 이상과 Identity 서비스 HTTP 호출까지 발생 |
| 확인한 원인 | `toBoothVehicles(Booth)`가 부스 1개당 게시글, 차량, 참가업체명(자체 쿼리 + Identity HTTP 호출), 신청그룹ID를 각각 조회하고 `toVehicleResponse`가 차량마다 이미지도 추가 조회해 부스 x 차량 단위로 쿼리가 곱셈으로 늘어남. 같은 서비스의 `listMyBooths()`는 이미 JOIN FETCH로 N+1을 피했지만 이 메서드는 그 컨벤션을 따르지 않았음 |
| 조치, 담당자 | 부스 목록 조회 후 필요한 데이터를 고정 쿼리 몇 번으로 배치 조회하도록 재작성. `BoothApplicationRepository.findByBooth_Expo_Id()`로 신청 내역을 한 번에 맵으로 변환, `findByBooth_IdIn` 등 IN 절 배치 조회 리포지토리 메서드 추가, Identity 호출은 exhibitorId 기준 캐시 맵으로 exhibitorId당 1회만 호출 |
| 정상, 실패 회귀 | N+1 제거 후 부스 통합 화면에서 전 부스의 차량이 정상 노출되는 것을 확인 |
| Backlog, 설계 조정 | `CustomerVehicleService.searchVehicles()` 등 이후 추가된 기능에서 같은 N+1 패턴이 재발한 사례가 있어 정기 점검 필요 ([[project-post-demo-todo]] 트래픽 검토 참고) |

## 필드 1개짜리 요청 DTO에서 Jackson 역직렬화 실패

| 항목 | 기록 |
|---|---|
| 시각, 영향 | 필드가 하나뿐인 요청 DTO(PasswordResetRequest, RefundRequest, EmailRequest)에 정상 JSON을 보내도 역직렬화가 실패하고 500 에러 발생 |
| 관련 Story | 비밀번호 재설정, 환불 요청, 이메일 인증 재발송 (Notion 원본 확인 필요) |
| 관련 계약, Test | `PasswordResetRequest`, `RefundRequest`, `EmailRequest` |
| 재현, 증상 | `{"email": "user@example.com"}`을 보내면 `MismatchedInputException: Cannot deserialize value of type java.lang.String from Object value` 발생 |
| 확인한 원인 | Jackson은 파라미터가 1개뿐인 생성자를 만나면 JSON 객체 전체를 그 파라미터 타입에 그대로 바인딩하려는 delegating creator로 판단함. 필드가 둘 이상이면 자동으로 프로퍼티 기반 생성자로 인식하지만 1개일 때는 구분 근거가 없어 delegating 쪽으로 기욺. `@AllArgsConstructor`로 만든 생성자에는 파라미터 이름 정보도 없음 |
| 조치, 담당자 | 생성자에 `@JsonCreator(mode = JsonCreator.Mode.PROPERTIES)`를 붙이고 각 파라미터에 `@JsonProperty`로 JSON 필드명을 직접 지정. Lombok `@AllArgsConstructor` 대신 생성자를 직접 작성. 같은 증상의 `RefundRequest`에도 동일 적용, 이후 만든 `EmailRequest`는 처음부터 이 패턴 적용 |
| 정상, 실패 회귀 | 세 DTO 모두 정상 JSON 요청으로 역직렬화 성공 확인 |
| Backlog, 설계 조정 | 필드 1개짜리 요청 DTO를 새로 만들 때 이 패턴을 기본으로 적용하도록 컨벤션화 |

## Gemini AI 호출에 횟수, 토큰 제한이 없어 비용이 무제한으로 늘어날 수 있음

| 항목 | 기록 |
|---|---|
| 시각, 영향 | 상담 요약, 리드 이메일 초안, AI 후기 초안, 후기 문장 다듬기, 자연어 차량 검색, 차량 이미지 AI 분석 6개 기능 모두 호출 비용을 제한하는 장치가 없었음 |
| 관련 Story | AI 차별화 기능 전반 (Notion 원본 확인 필요) |
| 관련 계약, Test | Gemini(3.5 Flash-Lite) 연동 6개 API |
| 재현, 증상 | 요약, 초안류 3곳은 버튼을 누를 때마다 횟수 제한 없이 API 호출. 자연어 차량 검색은 검색어와 무관하게 모든 차량을 후보로 보내 차량이 늘수록 검색 1건 비용이 계속 커짐 |
| 확인한 원인 | 요약, 초안류는 재생성 버튼을 추가하면서 버튼 1번이 API 호출 1번이라는 비용을 고려하지 않음. 차량 검색은 결과 정확도만 검증했고 후보로 보내는 개수(토큰 수)는 검토한 적이 없음 |
| 조치, 담당자 | 상담, 리드 건마다 카운터를 두고 4번째 호출부터 409로 차단(재시도 3회, 실패해도 호출은 차감). 차량 검색은 검색어에서 가격, 차종 조건이 보이면 Gemini 호출 전 SQL로 후보를 먼저 거르는 사전 필터링 추가. 조건이 없거나 결과가 0대면 전체 후보로 되돌리는 안전장치 포함 |
| 정상, 실패 회귀 | 실측: "5000만원 이하 SUV" 검색(차량 20대)에서 promptTokenCount 1,755 -> 622로 64.6% 감소, 설명 손실 없음. "가족용" 같은 조건 없는 검색은 20대 그대로 유지되어 정확도 보존 확인 |
| Backlog, 설계 조정 | 후기 문장 다듬기, 차량 이미지 AI 분석은 횟수를 셀 대상이 없어 제한을 아직 적용하지 못함. 향후 계획으로 남겨둠 |

## 로그인, 인증코드 발송, 비밀번호 재설정에서 이메일 존재 여부 노출 (타이밍 공격)

| 항목 | 기록 |
|---|---|
| 시각, 영향 | 로그인, 이메일 인증코드 발송, 비밀번호 재설정 요청 세 API 모두 이메일 가입 여부에 따라 응답 시간이나 응답 내용이 달라져, 비밀번호 없이도 특정 이메일의 가입 여부를 알아낼 수 있었음 |
| 관련 Story | 인증, 계정 보안 전반 (Notion 원본 확인 필요) |
| 관련 계약, Test | 로그인, 이메일 인증코드 발송, 비밀번호 재설정 요청 API (identity) |
| 재현, 증상 | 로그인은 존재하지 않는 이메일 쪽이 응답이 더 빠름. 인증코드 발송은 가입된 이메일에 바로 409 반환. 비밀번호 재설정은 가입된 이메일에만 실제 메일을 보내고 미가입 이메일은 아무 동작 없이 200만 반환 |
| 확인한 원인 | 로그인은 이메일이 없으면 즉시 예외를 던지지만 있으면 BCrypt 해시 비교까지 실행한 뒤 실패 처리되어, 의도적으로 느리게 설계된 BCrypt 연산 유무만큼 응답 시간 차이가 발생. 인증코드 발송과 비밀번호 재설정은 가입 여부에 따라 응답 메시지, 상태 코드, 실제 메일 발송 여부 자체를 다르게 만들어 시간차를 잴 필요도 없이 노출됨 |
| 조치, 담당자 | 로그인은 이메일이 없어도 항상 더미 해시와 BCrypt 비교를 한 번 실행하도록 수정해 두 경우의 연산 비용을 동일하게 맞춤. 인증코드 발송은 가입 여부와 무관하게 항상 코드를 발송하고 200을 반환하도록 변경(중복 가입 차단은 회원가입 시점으로 이동). 비밀번호 재설정은 미가입 이메일에도 실제로 메일을 보내되 내용만 "가입 내역이 없습니다"로 다르게 처리 |
| 정상, 실패 회귀 | 세 API 모두 가입, 미가입 이메일에 대해 응답 코드와 처리 시간이 동일해지는 것을 확인 |
| Backlog, 설계 조정 | 계정 열거 공격 방지 원칙(성공, 실패 경로가 같은 연산과 I/O를 거치게 만들기)을 신규 인증 관련 API에도 기본 체크 항목으로 적용 |

| 확인한 원인 | MySQL Connector/J의 `preserveInstants` 옵션(기본값 true)이 JVM 기본 시간대와 커넥션의 `serverTimezone`이 다르면 그 차이만큼 값을 추가로 변환함. MySQL 컨테이너에는 `TZ: Asia/Seoul`을 지정했지만 백엔드 서비스가 실행되는 JVM 자체의 기본 시간대는 어디에도 명시하지 않아 컨테이너 베이스 이미지의 기본값(UTC)에 맡겨져 있었고, `serverTimezone`을 맞춘 뒤에도 이 차이 때문에 값이 한 번 더 밀려서 변환됨 |
| 조치, 담당자 | JDBC URL에 `preserveInstants=false`를 추가해 드라이버의 추가 변환을 끔. 프로젝트가 모든 시각을 한국 시간 기준으로 다루고 있어 드라이버의 자동 변환 자체가 불필요했음 |
| 정상, 실패 회귀 | 체크인 시간, 통계 집계 시간 검증 테스트 재실행으로 시간 오차 해소 확인 |
| Backlog, 설계 조정 | 시간대 문제는 DB 쪽 설정만이 아니라 애플리케이션이 실행되는 JVM 쪽 기본 시간대도 함께 점검해야 한다는 점을 다른 서비스에도 동일하게 확인 필요 |
