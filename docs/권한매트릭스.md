# 권한 매트릭스

## 1. Role 정의

| Role | 대상 | 부여 시점 | 활동 |
| --- | --- | --- | --- |
| GUEST | 비회원 (로그인하지 않은 상태) | 토큰 없음 | 회원가입·로그인, 비밀번호 재설정, 공개 박람회 조회(`/api/customer/expos*`) |
| USER | 사이트를 이용하는 고객(회원) | 이메일 회원가입 시 Identity가 부여 | 박람회 방문 예약(QR), 셀프 체크인, 상담·시승 신청, 당일 입장권 결제, 마이페이지 |
| EXHIBITOR | 참가업체 (부스 운영 주체) | 사업자 인증 통과 후 이메일 가입 시 Identity가 부여 | 박람회·부스 조회, 부스 신청·결제, 담당 부스 콘텐츠·전시 차량 관리, 담당 부스 상담 승인/반려 |
| ADMIN | 관리자 (플랫폼 운영) | Seed 계정 (가입 API 없음) | 박람회·부스 등록·공개, 부스 신청 심사 |

> 로그인은 유형 무관 **이메일 방식으로 통일**(Sprint 1 Review). 사업자등록번호는 `^\d{3}-?\d{2}-?\d{5}$` 정규식으로 10자리(대시 optional, `SignUpService.normalize()`에서 제거)만 받는다 — 로그인 식별자가 아니다. `refresh`·`logout`·비밀번호 재설정은 `refreshToken` HttpOnly 쿠키 또는 메일 토큰으로 수행한다.
> 
> 
> 저장되는 `Role` enum은 `USER · EXHIBITOR · ADMIN` 3개(= `users.role` 컬럼, `Role.java`). `GUEST`는 토큰이 없는 상태를 가리키는 논리적 구분이며 별도 값으로 저장하지 않는다. JWT `role` 클레임 → Gateway가 `X-User-Role`로 전달 → Service가 `ROLE_<role>` 권한으로 매핑(`GatewayAuthenticationFilter`).
>

## 3. 외부 API 권한 (`/api/**`)

**인가 메커니즘.** Gateway(`JwtAuthenticationFilter`)가 accessToken 서명·만료를 검증해 `X-User-Id`·`X-User-Role`을 하위 Service에 주입하고, 클라이언트가 보낸 동일 헤더는 먼저 제거한다. 화이트리스트(토큰 없이 통과): `/api/auth/**`, `/oauth2/**`, `/login/oauth2/**`, `/api/customer/expos`·`/api/customer/expos/{id}`·`/api/customer/expos/{id}/booths`·`/api/customer/expos/{id}/vehicles`, `/api/customer/vehicles/search`, `/api/customer/booths/{id}/reviews`, `/uploads/**`, `/swagger-ui/**`, `/v3/api-docs/**`, `/webjars/**`. `OPTIONS`는 화이트리스트와 별도 로직으로 무조건 통과.

각 Service는 `GatewayAuthenticationFilter`(common 모듈)로 이 헤더를 `ROLE_<role>` 권한으로 매핑하지만, `SecurityConfig`의 경로별 강제 규칙은 서비스마다 다르다³:

- **Identity**: `/api/admin/users/**`만 `ADMIN` 강제, 나머지는 `permitAll()` 후 컨트롤러(`MeController` 등)가 개별 검증.
- **Expo**: `/api/admin/**`→`ADMIN`, `/api/exhibitor/**`→`EXHIBITOR`, 고객 하위 경로 일부(`consultations/**`, `expos/*/visited-booths`, `notifications/**`)만 `USER` 강제, 나머지 `permitAll()`.
- **Reservation**: `/api/customer/**`→`USER`, `/api/admin/**`→`ADMIN`.
- **Payment**: `/api/exhibitor/payments/**`→`EXHIBITOR`, `/api/customer/admission-payments/**`→`USER`, `/api/admin/**`→`ADMIN`.

미인증 `401`·역할 불일치 `403` 응답은 Gateway·Service 모두 공통 실패 Envelope를 사용한다.

## 4. 내부 API 권한 (`/internal/**`)

Gateway·외부 OpenAPI에 노출하지 않는다. 호출 주체는 환경 변수 Bearer Token(`SVC_TOKEN_<caller>`)으로만 검증하며, 사용자 토큰·Role은 사용하지 않는다.

| 호출 Service → 대상 | Resource·행동 | 내부 인증 | 업무 조건 | 허용 | 실패 |
| --- | --- | --- | --- | --- | --- |
| Expo·Review → Identity | `getUser`(`GET /internal/identity/users/{userId}`) 사용자 정보 조회 — 참가업체 회사명/업종(Admin 심사 화면), 후기 작성자 이름 표시용 | `Bearer ${SVC_TOKEN_EXPO}` 또는 `${SVC_TOKEN_REVIEW}` 또는 `${SVC_TOKEN_RESERVATION}` | 사용자 존재 | `{ companyName, industry, businessNo, representativeName, email, name }` | 토큰 불일치·누락 `401` / 없는 사용자 `404` |
| Reservation → Identity | `getUserNames`(`GET /internal/identity/users/names?ids=...`) 고객 이름 일괄 조회(관리자 입장 현황용) | `Bearer ${SVC_TOKEN_RESERVATION}` | — | `{ userId: name }` 맵 | 토큰 오류 `401` |

## 5. 판정 순서

모든 요청은 아래 순서로 판정한다. 앞 단계에서 실패하면 뒤 단계를 평가하지 않는다.

1. **인증 유효성 (Gateway)** — accessToken 서명·만료 검증. 실패 또는 보호 경로에 토큰 없음 -> `401` + `WWW-Authenticate: Bearer`. 성공 시 `X-User-Id`·`X-User-Role` 주입(클라 위조 헤더 제거). `/api/auth/**`·`/api/customer/expos*`·`OPTIONS`는 화이트리스트.
2. **Role (Service)** — Gateway 헤더를 Spring Security SecurityContext로 매핑, 경로 규칙으로 판정. 미인증 상태로 보호 경로 도달 `401`, 요구 Role 불일치 `403 FORBIDDEN` + 감사 로그.
3. **Resource 존재와 소유 관계** — 없으면 `404`, 타인 소유면 `403`(§6 참조)
4. **업무 상태** — 상태 전이·중복·기간 위반 시 `409`
5. **Dependency 결과** — 확인 불가 시 `202`/`503`로 안전하게 실패. **Dependency 장애를 `403`으로 오인시키지 않는다.**
6. **허용** 또는 안전한 실패

## 6. 403 vs 404 선택 근거

| 상황 | 선택 | 근거 |
| --- | --- | --- |
| 타인 소유 BoothApplicationGroup·Payment·Ticket·Consultation 조회 | `403` | ID는 순차·추측이 어렵고, 접근 시도를 감사 로그로 남기는 편이 운영 추적에 유리 |
| 타인 담당 Booth 콘텐츠·전시 차량 접근 | `403` | 위와 동일 |
| 존재하지 않는 리소스 | `404` | 리소스 부재 |
| `ADMIN`/`EXHIBITOR`/`USER` 전용 경로에 다른 Role 접근 | `403` + 감사 로그 | 경로 자체가 특정 Role 전용임이 명확 |

민감도가 더 높은 리소스가 추가되면(예: 개인정보 상세) 추측 방지를 위해 `404`로 바꾸고 이 표에 근거를 기록한다.

## 7. 감사 로그 대상

- 모든 `403` 응답 (`userId`, `role`, `method`, `path`, `X-Trace-Id`, `ts`)
- 전용 경로에 대한 권한 없는 접근 시도
- 타인 소유 리소스 접근 시도
- 로그에 비밀번호·토큰·연락처 원문을 남기지 않는다.
